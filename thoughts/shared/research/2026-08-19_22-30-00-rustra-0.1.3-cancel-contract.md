# 리서치: rustra 0.1.3 취소 API ↔ Glimpse 취소 경로 정합

**질문**: rustra 0.1.3의 `InvokeOptions.signal`(T1 취소)을 Glimpse의 기존
`cancel_download` 플래그 방식에 어떻게 정합할 것인가 — 라운드 4 후보의 입력 정리.

## rustra 0.1.3 취소 표면 (`@rustra/types` dist/index.d.ts)

- `invoke<T>(command, args, options?: InvokeOptions)` — **생성 코드 전 커맨드에
  `options` 전파 추가됨** (bridge:generate 재실행으로 Glimpse generated/에 이미 반영)
- `InvokeOptions.signal?: AbortSignal` — abort 시 프라미스 즉시 reject +
  네이티브 취소 전파(엔진이 지원하면)
- `invokeBatch` 항목별 `options.signal` 취소
- `invokeTypedAsync` id 노출 → JS에서 항목 취소 가능

## Glimpse 기존 취소 경로

- 데스크톱 `cancel_download` 커맨드 (`commands.rs:61`) → `download_cancels`
  플래그 레지스트리 → 다운로드 루프의 `is_cancelled` 폴링. **Tauri 커맨드는
  rustra dispatch 밖의 손글 경로** — rustra 취소와 만날 곳이 없다.
- bridge `#[command]` 26개는 전부 동기 도메인 CRUD — 장기 실행 작업이 없어
  취소 수요 자체가 없다.

## 결론

1. **지금 정합할 것이 없다.** 취소가 필요한 유일한 장기 작업(모델 다운로드)은
   rustra 경로 밖의 Tauri 커맨드이고, rustra 경로 내 커맨드는 전부 짧은 동기 CRUD.
2. 라운드 4에서 다운로드를 rustra 커맨드로 흡수할 일이 생기면 그때
   `InvokeOptions.signal` → 폴링 플래그 브릿지(abort 이벤트에서
   `download_cancels.request` 호출)가 자연스러운 이음매가 된다.
3. 생성 코드의 `options` 파라미터는 하위 호환(선택)이라 호출부 변경 0.

**Why:** 불필요한 재연결을 막고, 흡수 시점에 참조할 수 있게 기록.
**How to apply:** 라운드 4 다운로드 흡수 논의 시 이 메모의 2번 안을 먼저 검토.
